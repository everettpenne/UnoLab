# Uno Lab 0.3.5

The assistant gesture actually opens Uno's search now.

## What's fixed

Three separate faults, each of which alone was enough to leave the gesture doing nothing or opening the wrong thing:

1. **The role could not be granted at all** (fixed in 0.3.4, but it needed this release to be usable): Android's `AssistantRoleBehavior` requires `sessionService`, `recognitionService` **and** `supportsAssist` in `voice_interaction.xml`. 0.3.3 declared only two, so the system logged *"unqualified voice interaction service"* and refused the role.
2. **The session never started.** The service names in that XML were relative (`.AssistSessionService`), which the framework resolves against the *package* name — so the component it tried to bind did not exist. They are now fully qualified.
3. **The hand-off landed in the wrong app.** Two causes: Uno Launcher is a home app, so it carries no `CATEGORY_LAUNCHER` filter and `getLaunchIntentForPackage` returns null (the activity is now named directly); and Android's package visibility hid the launcher from Uno Lab entirely, so even the named activity would not resolve — a `<queries>` entry fixes that.
4. **The session waited for screen data that a launcher never sends.** With no assist structure, `onHandleAssist` never fires and an empty session overlay sat in front of everything. The session now opens search on `onShow`, 250 ms later at most, and takes the screen's text when it arrives in that window.

## Verified on a Pixel 10a

With the assistant role held: the assist gesture opens Uno's search, and the session hands over cleanly (the fixes were found by watching the real logs, not by reasoning).
